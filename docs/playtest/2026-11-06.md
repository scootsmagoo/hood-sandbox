## Findings

1. **Soak FAIL: CPU per draw call drifted up.** The soak summary: `FAIL 15 min on desktop-medium ... cpu 9.78 -> 19.54 us/draw (limit 14.21)`. Per-minute samples ranged 10 to 30 us/draw with no clear trend after minute 4. The heap was flat (0.1 MB/min). This is one run on a shared host, so it may be noise or a real regression. I did not investigate the cause.
2. **Stuck event recorded by the bot.** The `stuck` counter went to 1 at minute 0.75 and stayed at 1 to the end. The log has no matching unstick counter, so the bot's own counters do not show whether the actor recovered. Location not identified from the log.
3. **Test setup: the soak needs baked tiles that a fresh clone does not have.** `public/tiles/` is gitignored. A first soak attempt on a bare clone drove 0 m, as the pitfall in the test skill predicts. The rerun used the M1 and M2 tile folders copied (read-only) from the local working copy, which holds a local bake and not a build tied to commit 5363a29. The tiles were not committed.
4. **Host noise, not a game bug.** The Vite dev server logged about 2,640 `ENOSPC: System limit for number of file watchers reached` lines during the soak and the controls check. The host's inotify instance limit is 128 and many desktop apps are running. The server kept serving frames. This is environmental.
5. **npm install warning.** esbuild and workerd install scripts are not on the allow list. Install still succeeded.

No `error` or `Uncaught` lines appear in game logs outside the watcher noise. Controls found no console errors.

## Suggestions

- Rerun the soak on a quiet host, and check the CPU drift against the previous nights before deciding it is a regression.
- Decide how the bot gets baked tiles: a published artifact, a bake step in the job, or a documented local copy with its commit recorded.
- Ask the owner to raise the inotify instance limit on the playtest host (`fs.inotify.max_user_instances`), or confirm whether the soak can run against a built `dist/`, to remove the watcher noise.
- Add the unstick counter to the soak summary so a single `stuck` event can be followed to recovery.
