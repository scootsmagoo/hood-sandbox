## Findings

1. **Soak bot failed on a JSON parse of HTML (setup gap, high confidence).**
   - Log: `the bot failed: SyntaxError: Unexpected token '<', "<!doctype "... is not valid JSON`
   - Cause: `src/main.ts:44` sets `DEFAULT_TILE = 'tiles/atlanta/m1-five-points/'`. That folder is generated by the bake pipeline and gitignored (`public/tiles/`), so a fresh clone does not have it. The server returns the SPA index.html for the missing tile.json, and the parse fails.
   - Effect: the soak never drove the car, so the 0 m/min and the "stuck?" line are a consequence of the failure, not evidence of a stuck car.
   - Controls printed "(no baked tile in public/tiles: skipping the real-tile check)", so the real-tile checks were skipped too. Only the procedural-ground checks ran.

2. **Possible app issue to verify (not confirmed).** `src/shared/protocol.ts:247` documents that "a failed load uses the procedural test ground". The bot instead hit an uncaught page error. Either the load path does not catch a JSON parse failure, or the fallback is not reached. This needs a look by a human; the bot did not isolate it.

## Not covered

The bot does not judge gameplay feel, design, difficulty, or whether the city looks right. The soak measures frame time, heap and draw calls. The controls check measures input responses. Neither is a playtest of fun.

## Suggestions

- Make soak fail fast with a clear message ("no baked tiles: run the pipeline or skip") instead of a JSON SyntaxError. Or have it skip with a labeled verdict, so a fresh clone is not mistaken for a regression.
- Add a CI or nightly step that bakes or downloads a small tile set, so the soak and real-tile controls run on every clone.
- Check the tile-load path against the protocol.ts fallback contract (finding 2).
- Consider a short doc note in the README that the soak needs `public/tiles/` from the pipeline.
